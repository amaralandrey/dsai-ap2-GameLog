**Goal:** fechar a issue #55: toda ferramenta do MCP respeita o escopo do token (leitura exige `ler`), o slug de jogo mesclado segue a mesma regra da API v2, a escrita recusada entra na auditoria com o código equivalente ao da API e o log de exceção vai, de forma explícita e testada, para o stderr.

Em `protocolo.py`, `iniciar` liga o logger do MCP ao stream `erros`. Nenhuma coluna muda (sem `./dev.sh reset`). A spec muda primeiro, num commit sozinho.

**Tech Stack:** Python 3.12, Flask 3, Flask-SQLAlchemy (SQLite), pytest.

**Spec:** `SPEC/2026-11-15-servidor-mcp.md` (MCP-05, MCP-07, MCP-08, MCP-10, MCP-12) · `SPEC/2026-11-15-api-v2-tokens.md` (AP2-04, AP2-06) · issue <https://github.com/amaralandrey/dsai-ap2-GameLog/issues/55>

## Premissas

1. **Todas as ferramentas de leitura exigem `ler`**, inclusive as de catálogo (`buscar_jogos`, `detalhes_jogo`, `disponivel_em`), como pede a issue. Um token só com `escrever` vê e chama só as 3 de escrita. A API v2 serve `/jogos` sem token, mas o MCP sempre roda com token e um escopo por ferramenta é a regra mais simples de ler e testar.
2. **Slug mesclado:** a API v2 responde 301 ao principal nas leituras (`mesclado_ou_404`) e 404 nas escritas (`visible_games()` puro). O MCP não tem redirecionamento, então replica o efeito: leitura (`detalhes_jogo`, `disponivel_em`) responde pelo principal; escrita (`marcar_status`, `avaliar`, `registrar_sessao`) devolve "jogo não encontrado".
3. **Auditoria da escrita recusada:** toda chamada de ferramenta de escrita com token válido grava `AuditoriaToken` com `metodo="MCP"`, `rota="mcp:<ferramenta>"` e `status_http` igual ao que a API v2 gravaria: 200 sucesso, 403 escopo, 404 jogo não encontrado, 422 argumento ou regra recusados, 429 limite. Ferramenta de leitura não audita (a API também não audita GET). Token revogado não audita (a API não audita 401).

### Task 4: Log de exceção no stderr recebido (MCP-01)

**Files:**

Conferido em 2026-11-26 com um teste descartável: hoje nada liga o logger `app.mcp.protocolo` ao stderr. Em produção o traceback só chega ao stderr pelo `logging.lastResort`, porque nenhum handler existe. Sob pytest, o handler de captura no root engole o log e `r.stderr` da CLI vem vazio. Por isso a issue diz que o teste não prova nada. O fix torna o destino explícito: `iniciar` já recebe `erros`.

**Interfaces:**
- Produces: `iniciar(texto_token, entrada, saida, erros) -> int` com a mesma assinatura. Depois de autenticar, adiciona `logging.StreamHandler(erros)` a `log` e põe `log.propagate = False` enquanto `servir` roda; num `finally`, remove o handler e volta `log.propagate = True`.
